Clipper

Replays for games the way you actually remember them: the last 30 seconds are always on disk. Press a key, the clip is already written. Built for Linux and Windows.

In progress Rust FFmpeg PipeWire Windows Graphics Capture
View source

The problem

Game clippers record continuously and cut the file afterwards. That works for editing, not for reaction content, because the moment you actually want happened thirty seconds ago and the footage exists in a hundred-hour file nobody wants to scrub. This keeps a rolling window of encoded frames in memory and dumps the last N seconds on a keypress. The insight is that the muxing has to happen during capture, not after it.

Why these choices

  • Encode during capture, not after. Keeping raw frames would be simpler and would immediately exhaust memory at 1080p60. Once a frame is an H.264 packet it's tens of kilobytes instead of megabytes, which is what makes a 30 second rolling window fit at all.
  • FFmpeg's libav* bindings, not a wrapper crate. The crates wrap the C API so well they hide it. Going through ffmpeg-sys directly means owning the AVPacket lifetime, which is exactly the part this project is about.
  • Two capture backends, one interface. PipeWire on Linux, Windows Graphics Capture on Windows. Same trait, so the muxer never knows which OS it is on.
  • Crossbeam channels over std::mpsc. Bounded channels with capacity 1 give backpressure for free: if encoding falls behind capture, the producer blocks instead of growing an unbounded queue until the machine dies.
  • One muxer thread owning all FFmpeg state. Encoders aren't thread-safe. Funnelling both audio and video through a single struct means no locking and no shared mutable state across threads.

The rolling buffer

This is the whole idea. Every encoded packet goes into a VecDeque tagged with the time it arrived. Adding a frame evicts anything older than the window. On a keypress the muxer writes what's currently in the deque, which is by definition the last 30 seconds. 640 bytes to 200 MB and growing, with no seeking.

rustsrc/capture/replay.rs
pub fn add_frame(&mut self, packet: Packet) {
    let now = Instant::now();

    self.bytes = self.bytes.saturating_add(packet.size().max(0) as usize);
    self.frames.push_back((packet, now));

    // evict memory hungry old frames
    while let Some((mut oldest_packet, oldest_instant)) = self.frames.pop_front() {
        if now.duration_since(oldest_instant) > self.duration {
            unsafe {
                self.bytes = self
                    .bytes
                    .saturating_sub(oldest_packet.size().max(0) as usize);

                let mut packet_ptr: *mut AVPacket = oldest_packet.as_mut_ptr();
                let raw: *mut *mut AVPacket = &mut packet_ptr as *mut *mut AVPacket;

                sys::av_packet_unref(packet_ptr);
                sys::av_packet_free(raw);
            }
            self.frames.pop_front();
        } else {
            break;
        }
    }
}

av_packet_unref frees the packet's buffers, then av_packet_free frees the struct itself. Doing only the first leaks the struct; doing only the second leaks the data. Both, in that order, is the only correct combination.

Freeing on drop

Because AVPacket owns heap memory that the garbage collector knows nothing about, the compiler will not clean it up. Drop drains the queue and frees every packet explicitly. Without this, every clip leaks a few hundred megabytes.

rustsrc/capture/replay.rs
// unref and free all packets using drain to take ownership of pointers
impl Drop for ReplayBuffer {
    fn drop(&mut self) {
        for (mut packet, _) in self.frames.drain(..) {
            unsafe {
                self.bytes = self.bytes.saturating_sub(packet.size().max(0) as usize);

                let mut raw: *mut ffmpeg_sys_next::AVPacket =
                    &mut packet as *mut _ as *mut ffmpeg_sys_next::AVPacket;

                sys::av_packet_unref(raw);
                sys::av_packet_free(&mut raw);
            }
        }
        self.frames.clear();
    }
}

drain(..) rather than iter() because freeing needs an owned handle. That's why av_packet_free takes a *mut *mut - it nulls out the pointer it was given.

Backpressure by construction

The video channel holds exactly one buffer. When capture outruns encoding, the producer waits instead of queueing. On Linux the audio channel is unbounded, which is a deliberate asymmetry - audio is a fraction of the data and dropping it visibly glitches in a way video doesn't.

rustsrc/capture/windows/video.rs
// capacity 1 = producer blocks when the muxer is behind
let (video_tx, video_rx) = channel::bounded::<VideoBuffer>(1);

Where it hurts

  • Audio and video aren't actually muxed yet. Both are encoded and both are buffered, but writing a valid interleaved output file is the missing piece. That's why the replay buffer is currently 3 seconds in muxer.rs, not 30.
  • The muxer is a god object. Roughly 400 lines holding both encoders, the scaler, the resampler, and all the PTS bookkeeping. It needs to split.
  • Keypress detection uses rdev, which is global and needs elevated permissions on Linux. A proper hotkey plugin would be less intrusive.
  • Timestamps are tracked manually as two i64 counters. Drift between audio and video is inevitable and there's nothing correcting it.
  • No crash safety. If the process dies mid-clip, the rolling buffer is gone. There's no way around that without writing continuously, which is the thing this design avoids.
